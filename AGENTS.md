# Flutter & Serverpod project

This project is a Flutter app (frontend) backed by a Serverpod server (backend). Always build the app's backend with Serverpod.

The user starts the server and Flutter app with `serverpod start`. There is no need to check if the server is running: make the changes and call the `serverpod` MCP tools as needed. If the server is not running, an informative error message will be received from the MCP server. Then STOP and ask the user to start it. NEVER start the server yourself. The Flutter app is started along with it, or can be launched from the MCP tool `spawn_flutter_app`.

While running, `serverpod start` watches for file changes to run incremental code generation and hot reload both the server and the Flutter app.

Calling `serverpod generate` directly is not needed, but might be useful to troubleshoot when an incremental generation fails.

ALWAYS use the MCP server instead of the command line. Use the MCP server to:

- `create_migration` and `apply_migrations` for database (after you change data models).
- `create_repair_migration` if the database has drifted out of sync with the migrations.
- `tail_server_logs` to read logs from the server.
- `tail_flutter_logs` to read the raw stdout/stderr of the Flutter app.
- `hot_reload` / `hot_restart` to reload or restart the server and the Flutter app. ALWAYS call `hot_restart` after doing changes in the Flutter app that may not work with normal hot reload (which is automatically applied).
- `spawn_flutter_app` to start a Flutter app declared under `serverpod: flutter_apps:` in the server `pubspec.yaml`.
- `get_flutter_app_dtd` (Dart tooling daemon) for connecting to the app through the `dart` MCP.

NEVER edit generated code. The server's `lib/src/generated/` directory and the whole `archive_client` package are rewritten by the code generator. Change the `.spy.yaml` models, the endpoints, or `lib/server.dart` instead.

Migrations are a narrow exception: the `migration.sql` of a generated migration MAY be edited by hand when the generated SQL would lose data — to add a data transformation, or to reach a destructive change through non-destructive steps. Never touch the other files in the migration directory, and keep the schema the SQL ends up with identical to `definition.sql` — new databases are created from that file and never run `migration.sql`.

Only when the server cannot be started at all, fall back to the CLI in the server package:

- `serverpod generate` to regenerate the client and the generated server code.
- `serverpod create-migration` after changing a model with a `table` (add `--force` for destructive changes). It only writes the migration; `serverpod start` applies pending migrations when it boots the server.

Tests need no Docker. `config/test.yaml` sets `database.dataPath`, so Serverpod starts and manages the test database (an embedded PostgreSQL) itself, and the project's `docker-compose.yaml` is not used for it. Just run `dart test` in the server package.

Checklist after doing changes, in this order:

- `dart analyze` (CLI)
- `dart format` (CLI)
- `create_migration` and `apply_migrations` (MCP - only if necessary)
- Do `serverpod` MCP `hot_restart` if required (hot reload is done automatically). Will also hot restart Flutter app
- Run tests, if applicable (`dart test` in the server package)
- Check `serverpod` MCP `tail_server_logs` and `tail_flutter_logs` for any issues.

CI pins Flutter 3.44.4 (Dart 3.12.2). When the local SDK differs, verify formatting with Dart 3.12.2 as well: newer formatters can produce different output even with the same package language version. The Format workflow prints the SDK version and the exact diff on failure.

If the user asks you to test the app:

1. Use `get_flutter_app_dtd` (`serverpod` MCP) to get the Flutter app's DTD
2. Pass the DTD to `connect_dart_tooling_daemon` (`dart` MCP) to connect to the app
3. Use `flutter_driver` (`dart` MCP) to navigate through the app

The app is launched from `archive_flutter/lib/driver.dart`, which starts the Flutter driver extension with text entry emulation turned off so the app stays usable by hand. To let the driver type, set `enableTextEntryEmulation: true` there and `hot_restart` the app.

## Archive application

Archive is a Ukrainian-language DESKTOP archive application with a dark green left sidebar. The Serverpod runner launches the `desktop` companion on `device: macos`, not a browser. Preserve this target unless the user requests another desktop OS.

- `archive_shared/lib/archive_schema.dart` defines the Ukrainian field schema (the public archive_shared.dart file re-exports it; the backend imports archive_schema.dart directly), calendar validation, card identity keys and permission rules shared by the server and Flutter.
- The management documentation and court case modules support manually entered, versioned cards. The fields follow the supplied archive architecture workbook.
- `ArchiveEndpoint` requires login and checks the database-backed member role and module permissions on every request. New users are pending; readers can read, editors can write in permitted modules, administrators can manage other users. Blocked users cannot read. An administrator cannot change their own access through this panel.
- Existing administrator identities and password hashes are preserved when migrating to usernames. The migration derives unique lowercase logins from legacy email local parts, using user-ID fallbacks for collisions. `archiveBootstrapAdminEmail`/`ARCHIVE_ADMIN_EMAIL` remains a legacy-only bootstrap path for existing email identities; username registration ALWAYS creates pending members and must never promote a user based on a chosen login. Fresh deployments require server-side initial administrator provisioning. Never put account credentials or bootstrap secrets in Flutter or source control.
- Authentication uses LoginEndpoint (username/password login and registration), AccountEndpoint (self-service password change and administrator reset), and official Serverpod JWT refresh/session storage. The credential adapter reuses the official EmailIdp Argon2 password hashing and persistent failed-login limiter; new accounts use opaque UUID@archive.invalid identifiers internally, with no mailbox, email endpoint, email delivery or verification codes. Legacy credentials keep their original internal identifier. Logins are case-insensitive, 3–64 ASCII letters/digits/dot/underscore/hyphen. Passwords are 8–256 characters. Password resets generate a random temporary password, revoke tokens and force a password change; no secrets are written into audit events. All archive operations reject passwordChangeRequired members, and online caches are purged until the password changes. Sessions and existing memberships must retain their user IDs.
- Import accepts `.xlsx` with headers in row 1, sheet selection, explicit column mapping, validation and preview. There is NO artificial total row, cell or workbook-size limit. Desktop parsing/validation run in a background isolate. Transfer uses byte-bounded batches, server-only staging tables and one final atomic upsert transaction with complete before/after audit events. Do not replace this with independently committed batches or reinstate the 500-row restriction. Progress, cancellation, idempotent append/commit and response-loss recovery are supported. Court identity is ONLY caseNumber (mandatory). Missing case numbers are counted and skipped during imports. Matching identities merge participant tuples (name, role, proceeding). Other nonempty values fill blanks by default, with an explicit overwrite option. The entire import dialog accepts desktop drag-and-drop of multiple .xlsx files (desktop_drop); macOS security-scoped access is released after reading. Calendar/format errors still block imports, but chronology inconsistencies are counted as non-blocking warnings and preserve the source dates. Several workbooks have independent reverse mappings (app field to Excel column) and automatic top summary validation. Do not reintroduce per-row duplicate warnings. Formula cells must first be replaced by values in Excel. `WorkbookService` uses `archive` and `xml`; the `excel` package is incompatible with Serverpod's `archive` dependency version.
- Saved cards in both modules support manually attached files. AttachmentEndpoint checks the parent card and current module rights for every operation. Server-only ArchiveAttachment/ArchiveAttachmentChunk tables store immutable content in bounded 256 KiB parts; uploads stay private to their creator until a size-checked atomic finish. Repeated append/finish calls are idempotent; interrupted uploads can be cancelled and expire after a day when new uploads begin. Attachments are soft-deleted with restore and metadata-only audit events. Card merges move all attachments to the surviving card in the same transaction; deleting/restoring a card hides/restores file access through the parent. Never log binary content or grant access based only on a supplied attachment ID.
- Native Drift schema 3 stores attachment metadata and binary parts in separate tables outside full archive snapshots, preserving parts on ordinary snapshot replacement. Accessible files download ahead for offline viewing; permission changes and logout purge metadata and binary content, with generation guards against late writes. Stream files to disk without assembling an entire file in the UI isolate. DesktopDocumentOpener explicitly creates the temporary/cache directory before writing (path_provider's macOS temporary path may not exist), flushes and closes the complete file, then opens its file URI through url_launcher/native NSWorkspace or ShellExecute; do not launch desktop files through subprocesses. Opening through the default app is limited to document/image extensions; other files can be saved. The card dialog preserves its original sequential sections, fonts and spacing. Keep the independently scrolling file panel on the right subtly contrasted with a light neutral gray background, white file cards and dark text; never use a dark or saturated green panel. Narrow windows stack the panel below. Keep the clamped information scroll independent of file operations. Record layout has a pure widget preview in record_layout.dart.
- Management nomenclatures are uploaded Word documents stored in the Serverpod database and opened with the default desktop application. These documents are limited to 5 MiB. `NomenclatureDialog` owns its controllers; never dispose controllers immediately after awaiting `showDialog`, since its closing animation has not necessarily finished yet.
- The server URL is a device-local application setting (`archive_settings.json` in application support; browser localStorage fallback), accessible before login and from the sidebar. ServerConnection owns URL, client and connection generation. Explicit HTTP(S) URLs are validated and normalized; saving the same URL is a no-op. A real switch prepares a fresh session without requiring connectivity, persists settings, pauses/invalidates the previous archive cache, clears its local authentication and replaces the entire MaterialApp navigator. Keychain token keys are scoped by canonical URL; migrate the legacy unscoped token only for the original default URL on first initialization. Late authentication responses cannot update a replacement connection. Settings contain no credentials. Keep the original default URL spelling for existing Drift cache keys.
- macOS uses the app's private legacy Keychain through `MacOsOptions(usesDataProtectionKeychain: false)`, as recommended by flutter_secure_storage for apps that do not need cross-app Keychain Sharing. It does not require a sharing entitlement or a provisioning profile. Keep authentication tokens in Keychain, never in the data cache.
- Inventory lists filter cards marked for inventory by manually specified long-term or permanent retention, with Excel export. Automatic category-based retention calculations are explicitly deferred by the user; do not invent legal retention rules.
- The related-case search button has been removed at the user’s request. Participant name, role and proceeding are stored together in validated participantDetails JSON within the card values; participants and proceedingNumber remain human-readable summaries. Never discard associations when merging or exporting. Deletions are soft and versioned, with undo and administrator audit recovery.
- Offline access is read-only. The last complete authorized snapshot is stored separately for each server/account. Native platforms use the Drift ORM SQLite database in the application support directory (local_database.dart and generated local_database.g.dart). Keep account isolation, atomic snapshot transactions and purge on permission revocation. Generate Drift code with build_runner; never edit it manually. Legacy JSON snapshots migrate once. Web fallback uses browser storage. Logout clears the cache, including after outstanding refreshes. All accessible nomenclature documents are downloaded in advance; admin snapshots include members and the audit journal. Authentication tokens are excluded from the database. Browser-storage capacity failures are shown in the UI. Revoked module access is purged when the server is next reachable.
- The card list reads 50-row pages from Drift, with a composite account/module/order index and Unicode search text. Keep search and export over the full archive, preserve offline access, and reset to page 1 when filters change. Native ORM snapshot processing and migrations run in background isolates; never move full JSON/ORM batches onto the UI isolate. Single-card saves update one local row and do not force an immediate full archive refresh. `ArchiveSyncEndpoint.watch` uses one authenticated bidirectional WebSocket, 25-second liveness frames and a 75-second expiring server-side presence lease. Data hints coalesce before fetching byte-bounded journal deltas; a five-minute reconciliation and reconnect replay cover missed notifications. `writeArchiveAudit(s)` serializes audit ID allocation until commit, and posts one hint when the request closes. ALL runtime audit inserts must use these helpers, otherwise a committed cursor can skip concurrent writes. `recordRevision` remains only for older clients. Persist delta rows/tombstones and their cursor atomically in Drift using ArchiveDeltaStore; do not rewrite the full snapshot on ordinary changes. A full reload is only needed for first sync, changed permissions or recovery from a lost local copy. Unchanged native snapshots update only profile/sync metadata; never rewrite every local row just to change a timestamp. `ArchiveActivity` feeds a short text-only status in the top-right header through `ArchiveStatusText`; do not add synchronization progress bars, byte counts or network metrics. Status changes must not rebuild the card list or change editor layout. The sidebar brand is «Архів». Import field mappings are grouped in inline sections matching the card, never tabs. Editors own a clamped scroll controller and align section fields to the left.
- Windows x64 clients check signed updates through unauthenticated `UpdatesEndpoint.check/download` RPCs on their configured API server. Keep these signatures backward-compatible. Releases are immutable SHA-256-named installers in `ARCHIVE_WINDOWS_RELEASE_DIR` (default `archive_server/updates/windows/x64` relative to the server); publish latest.json last and retain old binaries for in-flight downloads. No archive data or signing secrets belong in that directory. Ed25519 verifies the exact base64 payload with the pinned public asset; SHA-256 and size are checked before and immediately before installing. Never execute an unsigned/unverified server-supplied path or downgrade by build number. The updater runs only on Windows x64, checks before sign-in/at startup/every six hours/on URL switch, cancels stale-server results, and installs only on explicit user action. Preparation invalidates and drains pending cache writes without purging data. Inno Setup installs per-user with a fixed AppId and preserves Windows CompanyName/ProductName/executable name and AppData identities. The local `.release-keys/windows-update.key` is ignored and must never be exposed or committed. `tool/build_windows.ps1` packages the complete Flutter bundle and CRT; see `docs/windows-releases.md` for build/publication and native Windows verification. macOS updates are out of scope.
- Public GitHub releases from `k0zlov/archive` are synchronized to the server update directory every 5 minutes by GithubReleaseSync (override ARCHIVE_GITHUB_REPOSITORY, disable with ARCHIVE_GITHUB_UPDATES=false). Never send archive data or account/GitHub tokens in this process. Validate the signed manifest with config/windows_update_public_key.txt and hash/size of streamed installer before atomic publication; preserve current and older downloads on failure or rollback. The Windows workflow is manual via Run workflow, auto-increments builds from the last signed release, uploads assets to a draft and publishes only after success. Secrets come only from Actions secret ARCHIVE_UPDATE_PRIVATE_KEY; public client/server keys must match. GitHub hosting is public and only outgoing server HTTPS is needed.
- Signed Windows manifests include minimumSupportedBuild (legacy default 1). The mandatory workflow option raises it to the new build; ordinary releases preserve the previous minimum and must never lower it. WindowsClientPolicy blocks unsupported API calls with HTTP 426 and signals live clients through archiveSync.watch; public updates.check/download must always remain backward-compatible and available. ArchiveApiClient gates ordinary RPCs, authentication and streams before network access. Restore auth locally and check compatibility before initialization. Persist verified policies per canonical server URL, preserve archive/auth/file caches when blocked, and offer explicit update or read-only offline access. Never treat compatibility blocking as revoked authentication or purge caches. A first ordinary release must distribute this mechanism before enforcing a mandatory minimum; older clients cannot show a choice they do not implement.
- API compatibility is declared in archive_shared/lib/client_protocol.dart independently of application versions. Signed manifests carry clientProtocol (legacy default 1). Servers advertise only actually implemented archiveServerProtocols; preserve versioned old API behavior during transitions. GitHub sync paginates stable release history, caches signed manifests by asset ID, and retains the newest complete compatible installer per protocol. Never apply an incompatible release's mandatory minimum. Keep protocol-N.json and older binaries for recovery/downloads; global build numbers grow across all protocols, but minimumSupportedBuild is monotonic per protocol. Stable unauthenticated HTTP /client-updates/v1/check and /client-updates/v1/download/<hash>/<offset> bypass archive/auth gates and must remain backward-compatible alongside legacy updates.check/download. Bootstrap includes signed policy manifests for all supported protocols so clients enforce their own floor even when the latest target uses another protocol. Only HTTP 404 permits legacy fallback (protocol 1); malformed/offline responses fail closed to cached read-only access. An unsupported newer client retains update access and waits offline for a server upgrade. Deploy the server filter first, then an ordinary protocol-aware client release before publishing future incompatible protocols. See docs/windows-releases.md.
- AppearanceController persists the device-local ThemeMode (system/light/dark) in the same settings store as the URL. Native setting writes are serialized read/modify/write operations so changing or rolling back one setting never erases the other. MaterialApp has light/dark themes and follows OS changes in system mode without resetting the navigator or authentication. Keep foregrounds, surfaces, warnings, errors, form inputs, chips, record participants and file panels theme-aware via ColorScheme and ArchiveColors. Only the permanently dark green sidebar/brand has fixed matching colors. Do not reintroduce light-only black text or white card backgrounds. Tests check resolved text against actual ancestor surfaces in both themes.
- The Flutter data layer is under `lib/data`, views and state under `lib/ui`. `ArchiveController` can be injected into `ArchiveShell` for UI tests. Manrope and its OFL license are bundled to avoid font downloads offline.
- Tests cover server permissions, version conflicts, atomic imports, related searches, workbook mapping/date handling, cache isolation/revocation/logout races, responsive layouts and disabled offline editing.

- User presence and active-session counts are administrator-only. Presence snapshots are pushed over the authenticated stream; an offline UI must show unknown status, never stale online flags. Count live, unexpired presence leases grouped by user ID: each open watch/WebSocket connection counts once, even when two connections share the same authentication token. Saved sign-ins without an open connection do not count. Join official JWT tokens only to exclude revoked or expired credentials. Preserve the configured refresh-token lifetime when filtering. Never expose token secrets or auth IDs to clients. `AccountEndpoint.deleteMember` requires an administrator and forbids self-deletion, removes official auth credentials/profile/tokens, revokes all live connections and keeps a hidden anonymized ArchiveMember tombstone so a still-signed old JWT cannot bootstrap access. Preserve all historical archive/audit data. Deleted logins may be re-registered only as a new pending identity. A revoked connected client purges its local cache and auth, while an interrupted network connection retains read-only offline access. Password changes must not let the revoked old websocket clear the replacement session.

- ArchiveMaintenanceEndpoint exposes administrator-only destructive actions with exact typed confirmation: clearRecords deletes all cards in both modules, attachment metadata/parts and staged imports while retaining nomenclatures and audit; clearArchive also deletes nomenclatures and audit. Preserve all accounts, permissions, authentication, presence and server settings. Never execute these operations against the user's data merely to test the feature. Runtime archive/auth mutations use archiveTransaction's shared maintenance advisory lock; cleanup takes it exclusively before any row writes. ArchiveSyncState retains a reserved audit-sequence resetCursor even when audit is empty, forcing old clients to replace their cache after a purge even if later writes exceed the previous cursor. Never restart these sequences. Reset responses must purge local Drift rows and file parts before a full reload.
- CopyableValue overlays a small themed copy/check button in a permanent gutter; expose it on pointer hover or keyboard focus, preserve text selection and never shift text on hover. Copy displayed dates, raw case/participant values and individual role/name/proceeding values. Keep the case card's existing typography and section layout.
- Desktop launcher icons share `archive_flutter/assets/branding/app_icon.png`. Regenerate Windows ICO and macOS AppIcon assets using `dart run flutter_launcher_icons` in archive_flutter with flutter_launcher_icons.yaml; commit generated icon resources. Inno Setup uses the same ICO via SetupIconFile, while shortcuts and uninstallation use the executable's embedded icon. Native icon changes require a full rebuild and relaunch, not hot reload/restart. See docs/app-icon.md.
