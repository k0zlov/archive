# Windows: встановлення та оновлення Archive

Підтримується Windows x64. macOS/Linux не перевіряють і не встановлюють ці оновлення.

## Рекомендовано: одна кнопка в GitHub

Репозиторій `k0zlov/archive` публічний. GitHub збирає Windows-версію, підписує її й публікує в Releases. Serverpod сам перевіряє Releases кожні 5 хвилин і завантажує лише перевірений готовий пакет. Відкривати доступ до Mac з інтернету або копіювати файли вручну не потрібно. Клієнти продовжують отримувати оновлення через свій URL Serverpod.

Один раз:

1. Відправте актуальні зміни проєкту в GitHub разом із workflow та **відкритими** ключами `archive_flutter/assets/windows_update_public_key.txt` і `archive_server/config/windows_update_public_key.txt`.
2. GitHub → репозиторій → **Settings → Secrets and variables → Actions → New repository secret**. Назва: `ARCHIVE_UPDATE_PRIVATE_KEY`. Значення: один рядок із локального файла `.release-keys/windows-update.key`. Не додавайте приватний ключ до Git або Releases.
3. Переконайтеся, що на сервері запущена актуальна версія коду з цією інтеграцією. Токен GitHub для публічного репозиторію не потрібний.

Для кожного випуску:

1. Відправте готові зміни в GitHub.
2. **Actions → Windows installer → Run workflow**. Виберіть гілку з готовими змінами; за бажанням укажіть версію (наприклад `1.0.1`) та опис. Для несумісних змін увімкніть **«Обов’язкове оновлення для роботи із сервером»**. Натисніть **Run workflow**.
3. Дочекайтеся зеленого результату. У Releases буде `.exe` для першого встановлення. Сервер автоматично забере підписане оновлення протягом приблизно 5 хвилин, якщо GitHub і сервер доступні.

Якщо версію не задано, остання частина версії також збільшується автоматично (1.0.1 → 1.0.2). Номер збірки збільшується автоматично відносно останнього підписаного випуску та версії вихідного коду. Вручну змінювати pubspec для кожного випуску не потрібно. Поки файли не готові, випуск лишається чернеткою. Невдала збірка не замінює поточне оновлення.

Для перевірки у клієнті: «Налаштування» → «Оновлення» → «Перевірити». Клієнт також перевіряє при запуску й кожні 6 годин. Перед широким розповсюдженням перевірте перший установщик на одному Windows-комп’ютері.

За замовчуванням сервер читає `k0zlov/archive`. Інший публічний репозиторій: `ARCHIVE_GITHUB_REPOSITORY=owner/repo`. Вимкнути автоматичне отримання й користуватися ручною публікацією нижче: `ARCHIVE_GITHUB_UPDATES=false`. Каталог кешу задається наявним `ARCHIVE_WINDOWS_RELEASE_DIR`. Serverpod потрібен вихідний HTTPS до GitHub. Файли архіву та облікові дані не передаються в GitHub; синхронізація лише читає випуски.

Нижче описано резервний ручний спосіб.

## Обов’язкові оновлення

Спочатку випустіть і встановіть **звичайне** оновлення з підтримкою цього механізму. Раніше встановлені версії не мають екрана вибору й після блокування сервером можуть показувати звичайну помилку підключення; їх потрібно оновити через установщик.

Галочка обов’язкового оновлення встановлює `minimumSupportedBuild` у підписаному описі на номер нової збірки. Сервер застосовує цей мінімум лише після отримання перевіреного опису та готового установщика. Наступні звичайні випуски автоматично зберігають мінімум, а не скасовують попередню вимогу. Знизити його старим підписаним випуском також не можна.

При запуску Windows-клієнт перевіряє сумісність **до** входу, поновлення авторизації та завантаження архіву. Якщо його збірка застаріла, він пропонує:

- **Завантажити → Встановити й перезапустити** — після підтвердження користувача.
- **Працювати офлайн** — перегляд і пошук останньої локальної копії без змін. Потрібні збережений вхід і локальна база цього користувача на цьому сервері. Без копії застосунок повідомляє, що спочатку потрібне оновлення.

Обов’язковий режим зупиняє синхронізацію й звичайні запити, зберігаючи локальну базу, файли та вхід. Перевірка і завантаження оновлення залишаються доступними. Підписана вимога зберігається окремо для кожного URL і діє після перезапуску навіть без сервера. Якщо перевірка зв’язку не вдалася, доступна локальна копія й повторна перевірка.

Сервер також відхиляє запити застарілих Windows-клієнтів кодом HTTP 426. Активне підключення отримує вимогу оновлення під час наступного сигналу WebSocket (приблизно до 25 секунд, плюс кеш політики до 5 секунд). Поля платформи та збірки служать перевірці сумісності, а не замінюють авторизацію. Старі клієнти без цих полів вважаються застарілими, коли встановлено обов’язковий мінімум. Актуальні macOS/Linux-клієнти цей Windows-мінімум не обмежує.

Перед несумісною зміною серверного API підготуйте й опублікуйте працездатний установщик. Методи `updates.check` і `updates.download` та формат повідомлення про необхідність оновлення мають залишатися сумісними: інакше застарілий клієнт не зможе оновитися. Вимога діє для всього сервера, тому враховуйте час отримання випуску з GitHub перед розгортанням несумісного коду.

## Перша збірка на Windows

Потрібні Flutter 3.44.4, Visual Studio з **Desktop development with C++**, Inno Setup 6.3+ (із комплектною українською мовою), Git і PowerShell. Сценарій працює у Windows PowerShell 5.1 та PowerShell 7.

1. Перенесіть актуальний проєкт на Windows, включно з `archive_flutter/assets/windows_update_public_key.txt`.
2. Ключ підпису вже створено на Mac у `.release-keys/windows-update.key`. Для збірки установщика переносити його на Windows не потрібно. Збережіть окрему захищену резервну копію ключа; папка виключена з Git. Не надсилайте ключ у чат і не розміщуйте в каталозі публічних оновлень.
3. З кореня проєкту виконайте:

```powershell
powershell -ExecutionPolicy Bypass -File .\tool\build_windows.ps1 -InstallerOnly
```

Якщо Inno Setup встановлено в інше місце, додайте `-Iscc "C:\...\ISCC.exe"`. Для іншого розташування ключа є параметр `-SigningKey`.

Результат:

- `dist/windows/Archive-Setup-1.0.0-1-x64.exe` — установщик для першого встановлення. Ім’я залежить від версії у pubspec.
Параметр `-InstallerOnly` створює установщик без доступу до приватного ключа. Якщо ключ уже є на довіреному Windows-комп’ютері або у CI, запуск без цього параметра додатково створює `dist/windows/server/latest.json` і `<sha256>.exe`.

Збірка використовує `lib/main.dart`, включає DLL, ресурси Flutter, нативні бібліотеки та Visual C++ runtime. Сам exe недостатній для роботи Flutter, але всі ці файли містить один установщик.

Установлення відбувається для поточного користувача в `%LOCALAPPDATA%\Programs\Archive`, без адміністративних прав. Ідентифікатор Inno Setup незмінний. Назва виконуваного файла та Windows CompanyName/ProductName збережені для сумісності з раніше створеними кешами і захищеним сховищем.

## Публікація на сервері

Перенесіть зібраний `Archive-Setup-1.0.0-1-x64.exe` на Mac. У `archive_shared` виконайте (номер версії та збірки мають відповідати імені установщика):

```sh
dart run tool/windows_release.dart publish "/повний/шлях/Archive-Setup-1.0.0-1-x64.exe" 1.0.0 1 ../.release-keys/windows-update.key ../dist/windows/server
```

Після каталогу можна додати шлях до UTF-8 файла з описом змін (або `-` без опису), потім мінімальний номер сумісної збірки. Наприклад, для обов’язкової збірки 12: `... publish ... 1.0.12 12 ... ../dist/windows/server - 12`. Для ручної збірки PowerShell є `-MinimumSupportedBuild 12`. У наступних ручних випусках зберігайте цей мінімум; GitHub робить це автоматично. Підписаний пакет буде в `dist/windows/server`. Ключ залишається на Mac.

На Mac із Serverpod створіть каталог `archive_server/updates/windows/x64`. Скопіюйте туди **спочатку** `<sha256>.exe`, і лише потім атомарно замініть `latest.json` новим файлом (через тимчасове ім’я й перейменування). Не видаляйте попередні exe, поки користувачі можуть їх завантажувати. Імена файлів є адресами їхнього вмісту; не перезаписуйте старий exe іншим вмістом.

Для іншого каталогу задайте `ARCHIVE_WINDOWS_RELEASE_DIR` перед звичайним запуском `serverpod start`. Оновлення читаються без перезапуску сервера. Не кладіть у каталог приватні ключі, базу архіву чи особисті документи.

Публічні методи `updates.check` і `updates.download` працюють через **той самий URL API**, який користувач указав у налаштуваннях. Додатковий порт чи файловий сервер не потрібні. Перевірка працює до входу; облікові токени для завантаження не передаються.

## Наступна версія

1. У `archive_flutter/pubspec.yaml` змініть, наприклад, `version: 1.0.0+1` на `version: 1.0.1+2`. Число після `+` має **збільшуватися з кожним випуском**, навіть коли основний номер версії змінюється. Кожна з чотирьох числових частин має бути в діапазоні 0..65535.
2. За потреби створіть UTF-8 файл з коротким описом змін та додайте `-NotesFile .\release-notes.txt` до команди збірки.
3. Зберіть пакет тим самим ключем і опублікуйте, як описано вище.

Клієнт перевіряє версію при запуску, після зміни сервера, кожні 6 годин та кнопкою «Перевірити» у налаштуваннях. Звичайні оновлення можна відкласти. Для обов’язкового оновлення вибір — встановлення або автономний перегляд, як описано вище.

Опис версії підписано Ed25519; відкритий ключ вбудований у застосунок. Клієнт перевіряє підпис, тип продукту/архітектуру, номер збірки, довжину і SHA-256 установщика. Цілісність повторно перевіряється перед запуском. Дані йдуть порціями по 256 KiB без збирання всього exe у пам’яті. Зміна сервера скасовує старі перевірки та завантаження.

Кнопка «Встановити й перезапустити» спочатку зупиняє фонові оновлення локального кешу й чекає завершення записів. Установщик очікує виходу процесу, перевіряє інші запущені копії, оновлює файли та запускає застосунок. Він не видаляє AppData, Drift, налаштування або токени. Незбережені форми закриті модальними діалогами й недоступні для одночасного встановлення. Вхідні запити після підготовки не можуть заново записати старий кеш.

Це повний стиснений установщик, а не різниця між файлами. Підпис Ed25519 забезпечує довіру клієнта до оновлення; він не замінює Windows Authenticode. На першому ручному встановленні непідписаного Authenticode exe Windows може показати попередження про невідомого видавця. Якщо додаєте Authenticode, підписуйте exe **до** створення `latest.json`, інакше SHA-256 зміниться.

## Перевірка на Windows

1. Установіть версію `1.0.0+1`, увійдіть, задайте URL сервера й темну тему, дочекайтесь синхронізації.
2. Зберіть `1.0.1+2` і опублікуйте її на сервері. У старому клієнті відкрийте налаштування → «Перевірити».
3. Перевірте опис, завантажте, натисніть «Встановити й перезапустити».
4. Переконайтесь, що показано `1.0.1 (2)`, вхід, тема, адреса й локальні справи збережені. Без сервера справи мають залишатися доступними лише для читання.
5. Перевірте скасування завантаження, недоступний сервер, зміну URL під час завантаження та пошкоджений тестовий пакет. Пошкоджені/непідписані оновлення не повинні запускатися.
6. На тестовому сервері опублікуйте обов’язковий випуск. Перевірте блокування запитів і вибір офлайн-режиму, пошук та відкриття кешованих файлів без можливості редагування. Перезапустіть старий клієнт без сервера: вимога й локальні дані мають зберегтися. На чистому профілі без кешу офлайн-архів недоступний. Після встановлення нового випуску серверний доступ має відновитися.

## Збірка через GitHub Actions

Є ручний workflow `Windows installer`. Для нього потрібен секрет репозиторію `ARCHIVE_UPDATE_PRIVATE_KEY` — вміст **наявного** файла `windows-update.key` (один рядок base64). Не генеруйте інший ключ для кожної збірки. Workflow публікує готовий випуск у GitHub Releases; Serverpod автоматично забирає його. Додатковий артефакт `Archive-Windows` зберігається 14 днів для діагностики. Використовуйте цей спосіб лише в довіреному репозиторії з обмеженим доступом до секретів.
